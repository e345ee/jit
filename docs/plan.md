# План действий

## Фокус MVP

Приоритетный пользовательский сегмент: пациент, которому назначили обследование или медицинское действие с подготовительными документами и сроками. Первый сценарий для демонстрации: "МРТ с контрастом".

Формула проблемы:

Пациент перед диагностикой хочет быстро понять, какие документы и анализы нужны, где их получить и сколько они действуют, но информация разбросана между врачом, регистратурой, лабораторией, сайтом клиники и Госуслугами, из-за чего возникают ошибки, перенос записи и повторные обращения.

## Этап 1. Продуктовое уточнение

1. Зафиксировать 3-5 жизненных ситуаций для MVP.
2. Для каждой ситуации описать As Is и To Be.
3. Подготовить источники: официальные страницы, правила клиник, нормативные основания, дата актуальности.
4. Отметить, какие данные являются тестовыми или модельными.
5. Зафиксировать коммерческую формулировку: не "медицинский ИИ", а "навигатор маршрутов пациента".
6. Выбрать первого покупателя для пилота: диагностический центр, клиника, страховая ДМС или региональная организация.

## Этап 2. Контент и дерево решений

1. Создать схему карточки ситуации.
2. Создать схему шага: действие, зачем, где получить, срок, ошибки, источник.
3. Добавить условия адаптации: регион, аллергия на контраст, наличие направления, тип оплаты.
4. Заполнить минимум 3 карточки ситуаций и 5 карточек базы знаний.
5. Сделать проверку контента перед сборкой.
6. Описать pipeline анализа документов: источник -> извлечение требований -> карточка -> экспертная проверка -> публикация.
7. Назначить владельца контента и дату следующей проверки для каждой карточки.

## Этап 3. Mini app

1. Реализовать поиск и категории.
2. Реализовать карточку ситуации.
3. Реализовать экран деталей шага.
4. Реализовать локальный чек-лист.
5. Реализовать состояния загрузки, ошибки, пустого результата.
6. Проверить адаптацию под мобильный и web MAX.

## Этап 4. Bot

1. Подключить уже выданный токен MAX из локального `.env`.
2. Настроить стартовое меню.
3. Подключить mini app.
4. Реализовать опциональное напоминание.
5. Проверить, что основной сценарий проходит через MAX от начала до результата.

## Этап 5. Техническая упаковка

1. Добавить Dockerfile для web/api/bot.
2. Добавить compose.yaml.
3. Добавить `.dockerignore`.
4. Добавить lock-файлы зависимостей.
5. Добавить README с одной командой запуска.
6. Добавить тестовые данные и сценарий проверки.

## Этап 6. Проверка по критериям

1. Пройти основной сценарий 5 раз подряд.
2. Проверить отсутствие токенов в репозитории.
3. Проверить ошибочные действия: пустой поиск, недоступный API, неверный параметр карточки.
4. Проверить Docker-сборку до 5 минут без учета загрузки образов.
5. Подготовить презентацию: проблема, пользователь, решение, эффект, архитектура, масштабирование, риски.

## Этап 7. Подготовка к продаже и пилоту

1. Подготовить one-pager для клиники или диагностического центра.
2. Описать пилот на 2-4 недели: аудитория, канал входа, метрики, отчет.
3. Подготовить пользовательское соглашение, политику конфиденциальности и согласие на уведомления.
4. Если появится обработка персональных данных по поручению клиента, подготовить DPA/поручение на обработку данных.
5. Зафиксировать SLA и порядок обновления контента.
6. Подготовить контентное соглашение: кто утверждает медицинские и юридические формулировки.

## Метрики эффекта

- Сокращение времени поиска требований перед обследованием.
- Снижение числа пропущенных документов или просроченных анализов.
- Доля пользователей, дошедших от поиска до карточки и отметки шага.
- Доля пользователей, включивших напоминание.
- Количество повторных открытий карточки перед визитом.

## Что не делаем в MVP

- Не храним медицинские документы.
- Не загружаем пользовательские медицинские документы для анализа.
- Не подключаем реальные ЕГИСЗ, Госуслуги или клинические ИС.
- Не выдаем медицинские рекомендации.
- Не строим универсальный агрегатор всех услуг.
- Не делаем LLM-ответы без источников и контроля.
