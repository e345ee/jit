# Дальнейший план действий

## Цель ближайшего этапа

Довести проверяемую версию в MAX вокруг одного сильного сценария: пациент ищет "МРТ с контрастом", отвечает на 1-2 вопроса, получает карточку с шагами, сроками, источниками и локальным чек-листом, а при желании включает нейтральное напоминание.

## Принцип фокуса

Победная версия должна быть не самой широкой, а самой понятной. Поэтому сначала делаем один сценарий до конца, а остальные карточки используем как доказательство масштабируемости.

## Неделя 1. Уточнение продукта и контента

### 1. Зафиксировать продуктовую рамку

Результат:

- краткое название продукта;
- 1 абзац описания для заявки;
- целевой пользователь;
- ключевая проблема;
- ожидаемый эффект;
- список границ продукта.

Формулировка по умолчанию:

"Навигатор для пациента" - мини-приложение в MAX, которое превращает сложный медицинский маршрут в понятную карточку шагов, документов, сроков и типовых ошибок.

### 2. Выбрать демонстрационный сценарий

Основной сценарий:

- МРТ с контрастом.

Дополнительные карточки для масштаба:

- оформление инвалидности через МСЭ;
- налоговый вычет за лечение;
- подготовка к госпитализации;
- льготные лекарства.

### 3. Собрать источники

Для каждой карточки нужны:

- официальный или организационный источник;
- дата актуальности;
- регион применимости;
- что является фактом;
- что является допущением продукта;
- что нужно подтвердить экспертом.

### 4. Провести 3-5 коротких интервью

Кого спросить:

- пациент, который проходил МРТ/КТ/госпитализацию;
- администратор клиники или регистратуры;
- врач или медсестра;
- человек, оформлявший МСЭ или вычет;
- представитель пациентского сообщества, если есть доступ.

Главные вопросы:

- что было непонятно;
- где искали информацию;
- что забыли или боялись забыть;
- какие сроки вызвали путаницу;
- что пришлось уточнять по телефону.

## Неделя 2. Каркас приложения

### 1. Создать технический каркас

Компоненты:

- `web` - React mini app;
- `api` - контент и поиск;
- `bot` - входная точка MAX;
- `worker` - напоминания;
- `postgres` - напоминания;
- `redis` - очередь.

Минимальный локальный запуск:

```bash
docker compose up --build
```

### 2. Сделать схемы данных

Нужны схемы:

- `SituationCard`;
- `DecisionQuestion`;
- `Step`;
- `KnowledgeCard`;
- `SourceRef`;
- `Reminder`.

Обязательные поля карточки:

- название;
- описание;
- шаги;
- объяснения;
- где получить;
- сроки;
- частые ошибки;
- источники;
- дата актуальности;
- регион;
- статус данных: official, clinic, synthetic.

### 3. Реализовать первый пользовательский путь

Экраны:

1. Поиск и категории.
2. Список результатов.
3. Карточка ситуации.
4. Детали шага.
5. База знаний.
6. Настройка напоминания.

Состояния:

- загрузка;
- пустой поиск;
- ошибка сети;
- карточка не найдена;
- напоминание создано;
- напоминание не создано.

## Неделя 3. MAX и демо

### 1. Подключить выданный токен

Токен уже лежит локально в `.env` и не должен попадать в git.

Нужно:

- проверить старт бота;
- настроить команду `/start`;
- отправить кнопку открытия mini app;
- проверить, что mini app открывается из MAX.

### 2. Поднять HTTPS для mini app

Для хакатона mini app должен быть доступен по HTTPS.

Варианты:

- временный tunnel для разработки;
- облачный хостинг;
- статический хостинг для frontend + отдельный backend.

### 3. Проверить мобильную и web-версию

Минимальный чек:

- бот отвечает;
- mini app открывается;
- поиск работает;
- карточка открывается;
- чек-лист сохраняется локально;
- после перезапуска отметки остаются;
- напоминание можно включить и отменить.

## Неделя 4. Устойчивость, упаковка, презентация

### 1. Довести техническую комплектность

Нужно добавить:

- `Dockerfile`;
- `compose.yaml`;
- `.dockerignore`;
- lock-файл зависимостей;
- `openapi.yaml`, если API оставляем как отдельный проверяемый компонент;
- тестовые данные;
- README с одной командой запуска.

### 2. Проверить безопасность

Проверки:

- нет токенов в git;
- `.env` игнорируется;
- логи не содержат медицинских данных;
- пользовательские документы не загружаются;
- напоминание не содержит диагноза;
- все тестовые данные помечены как тестовые.

### 3. Подготовить презентацию

Структура:

1. Служебный слайд для проверки.
2. Пользователь и проблема.
3. Почему текущий путь сложен.
4. Решение.
5. Демонстрация сценария.
6. Архитектура.
7. Данные и безопасность.
8. Эффект и метрики.
9. Масштабирование.
10. Пилот и продажа.
11. Риски и ограничения.

### 4. Репетиция демо

Сценарий защиты:

1. Открыть бота в MAX.
2. Нажать кнопку mini app.
3. Найти "МРТ с контрастом".
4. Ответить на уточняющий вопрос.
5. Открыть карточку.
6. Отметить шаг.
7. Открыть объяснение шага.
8. Включить напоминание.
9. Показать источник и дату актуальности.

## Коммерческий трек параллельно

### 1. Подготовить one-pager

Для кого:

- клиника;
- диагностический центр;
- страховая ДМС;
- региональный оператор.

Что написать:

- какую проблему снимаем;
- какой сценарий запускаем первым;
- какие метрики измеряем;
- что требуется от партнера;
- срок пилота 2-4 недели.

### 2. Подготовить документы

Минимально:

- пользовательское соглашение;
- политика конфиденциальности;
- согласие на уведомления;
- медицинский дисклеймер;
- договор пилота;
- матрица ответственности за контент.

### 3. Описать пилот

Пилот:

- одна организация;
- один сценарий;
- QR или deeplink на памятках/стойке/сайте;
- отчет по метрикам;
- интервью после использования.

## Критерии готовности

Проект готов к проверке, если:

- основной сценарий проходит в MAX от начала до результата;
- есть минимум одна полностью заполненная карточка;
- чек-лист работает локально;
- источники и дата актуальности видны пользователю;
- есть обработка ошибок;
- Docker-запуск воспроизводим;
- README достаточно для проверки;
- презентация объясняет проблему, эффект и масштабирование;
- токены не попали в репозиторий.

## Приоритеты

### P0

- Каркас mini app.
- Карточка "МРТ с контрастом".
- Локальный чек-лист.
- MAX bot entrypoint.
- Docker.
- README.

### P1

- Напоминания.
- База знаний.
- Еще 2-4 карточки.
- OpenAPI.
- Тесты основного сценария.

### P2

- Кабинет редактора.
- Мультиязычность.
- Интеграции с клиникой или МИС.
- Загрузка пользовательских документов.

## Решения, которые нужно принять командой

1. Оставляем ли название "Навигатор для пациента" или придумываем более запоминаемое.
2. Первый пилот: клиника, диагностический центр или ДМС.
3. Основной регион для проверки.
4. Нужен ли маскот в демо или достаточно спокойного брендинга.
5. Делаем ли API обязательной частью сдачи или держим контент статическим на первом этапе.
